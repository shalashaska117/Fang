# Version 4 work plan

Version 4 starts from [v0.3.0-alpha.1](https://github.com/shalashaska117/Fang/releases/tag/v0.3.0-alpha.1), commit `8947c0aad087bbe9f50d5988c1ed4be06cf1272a`. This plan carries forward the 26 work items agreed before that release. It describes planned work, not capabilities of the released version. The [implementation checklist](V4-CHECKLIST.md) breaks these items into individual tasks and records their current status.

The target is competitive checked first-order reasoning on FOF and CNF: FNE, FEQ, unit equality and effectively propositional problems. ICU is an evaluation target. Results must include checking and the requested output. Typed logic, higher-order logic and arithmetic belong to the later versions in the [roadmap](ROADMAP.md).

## Starting measurements

The release's [benchmark report](https://github.com/shalashaska117/Fang/releases/download/v0.3.0-alpha.1/benchmark.md) is the v3 baseline. Earlier development measurements used different source revisions or conditions and must not replace it.

| Sample | Fang v3 counted results | Vampire counted results |
| --- | ---: | ---: |
| Mixed d286 | 180 / 286 | 235 / 286 |
| Satisfiable sample | 175 / 250 | 140 / 250 |
| TPTP 1000 | 267 / 1000 | 820 / 1000 |

A counted result needs a positive status, successful exit, no safety termination, a complete requested document and command wall time within 60 seconds. Fang also needs its compiled checker acceptance. The d286 Vampire total includes the incorrect nested-selection result discussed in the report. Sample memberships overlap; totals must not be added as if they were disjoint. See the report for paired timings and measurement limitations, and the [problem list](https://github.com/shalashaska117/Fang/releases/download/v0.3.0-alpha.1/fang-v3-vs-vampire-problems.txt) for every occurrence.

On the 1000-case sample, Fang returned 493 checked positive statuses. Of these, 226 lacked a complete document: 184 signed include bundles, 28 single-file distinct-object cases, 11 exporter rejections and three export timeouts. Fixing output is a separate task from finding more proofs. The include restriction is checked before other export restrictions, so removing it does not by itself establish that all 184 cases will produce documents.

## First integration milestones

Work proceeds on a branch based on the published v3 source. The released source, installation and benchmark evidence remain the reference.

- Item 14: both trace checker entry points now use an array clause store. Equivalence proofs preserve the complete result and every error. The source integration passed axiom audits for 1,596 declarations, 36 AST checks and 24 compiled-certificate replays against v3, with identical exits and output. The combined installation passed; end-to-end performance measurements remain open.
- Item 24: the 226 missing documents have been classified against their retained inputs. The cited exporter now has source-row rendering, proofs relating its rows to the original problem, and launcher routing based on the certificate producer. Focused checks and independent reviews passed. The compiled exporter passed 38 theorem audits, 12 Lean controls and 12 native IO controls. The installed launcher passed focused signed, distinct-object, nested-include, selection-list and multiple-conjecture tests. The historical regression produced 222 complete documents out of 226. An integrated export-deadline correction then recovered all three export-timeout cases in targeted installed checks. SWC279-1 also passed follow-ups, including the unchanged launcher; its earlier timeout remains unexplained. These runs are separate from the final benchmark.
- Item 22: component tests and independent reviews passed for compact function-cell SAT constraints and a function-free domain bound that includes Skolem constants. The launcher can retire a fully exhausted function-free model task without reporting a positive status. Ordinary bounded exhaustion and interrupted searches keep their retry behavior. Combined source-map checks and installation passed, including installed three-witness and dependent-witness model documents. Cross-size incremental solving and separate inferred-sort domains remain open.
- Item 20: UTF-8 comments passed a 202-module native rebuild, 48 compiled-certificate comparisons and an audit preserving the exact axiom sets of all 1,596 existing declarations. The structural UTF-8 validator itself has no axioms. Kernel input support, the `assumption` role and typed declarations remain separate work.
- Item 8: an isolated equality-factoring prototype passed bounded Rust reconstruction tests and Lean acceptance and rejection controls. A generated certificate now has a full kernel proof of acceptance and unsatisfiability from the original TPTP bytes: 16 instance modules, 33 theorem audits and 83 preserved helper audits. The full kernel route also rejects a corrupted claimed clause after exact-byte decoding. Parser compatibility with the older dialect is proved. TSTP correspondence proofs and seven output controls passed. The coherent native build passed all 1,634 fixed audits; the compiled checker and exporter accepted the original-input proof and rejected wrong claims and future parents. Product integration and independent review remain pending; the product search still disables this rule.
- Item 4: an isolated lazy-orphan heuristic distinguishes generating parents from proof parents through simplification. With an explicit passive-clause limit, it passed 30 Rust tests and 62 compiled-Lean certificate replays. A separate termination fix passed eight queue-exhaustion regressions against a reproduced V3 loop. The changes are integrated and passed the same controls on installed binaries. Orphan deletion remains disabled by default and the passive limit is unset. The passive limit does not bound all stored proof records or total memory. Optional limits now also count stored proof records and generated conclusions. They passed 122 installed compiled-Lean replays and 34 boundary refusals; both remain unset by default and are not total-memory limits. Compact literal arrays are also integrated and qualified. Two training inputs at fixed work retained identical search counters; the larger comparisons reduced median process RSS by about 9% and 11%, while one smaller comparison increased it by about 2%. No general performance improvement is inferred from these profiles.

The array checker source integration and cited exporter components have independent reviews. The combined production installation passed 4,449 Lean build jobs, 1,634 fixed declaration audits, 1,000 Rust tests (three ignored, including an explicit storage profile), formatting and Clippy. Its launcher passed the installation self-check, 12 positive runtime cases with complete requested documents, two include-selection rejections and a malformed-UTF-8 rejection. Focused kernel compatibility tests separately check the existing helpers and concrete certificates against both checker versions. This qualifies the current integrated milestone; V4 remains incomplete, and no end-to-end speedup is claimed.

- Item 6: optional bounded LPO ordering is integrated and passed 40 installed compiled-Lean certificate replays. KBO remains the default. Additional KBO weights and literal-selection policies are integrated and qualified with 360 installed compiled-Lean replays. Bounded DAG variable counting is also integrated and qualified with 366 byte-identical installed certificate replays. Training-based schedule selection remains open.

- Item 5: bounded ground congruence closure, unit-equation ground-joinability redundancy, critical-pair scores, connectedness and ground-goal transformation are integrated as optional producer features. Goal transformation reconstructs proofs over original inputs with unchanged certificate rules. The qualified final-unit-resolution extension recovers three training regressions; its installation passes 1,022 Rust tests and 164 compiled proofs with complete documents. Training leaves the defaults unchanged: scoring variants are complementary, and the other options have not established a coverage gain. Final strategy selection remains open.

- Items 7 and 11: exact ground-unit retrieval is integrated and qualified after profiling the six retained slow targets. Twenty fixed-work comparisons preserve inference counters and certificate bytes; four timed pairs are excluded. The index reduces subsumption calls substantially on the CSR cases but adds no solves in the recorded full producer follow-ups. The original block-21000 fixture already produces a checked finite model and complete output. See [V4-SEARCH-PROFILE.md](V4-SEARCH-PROFILE.md).

- Item 9: an isolated EPR producer now grounds clauses, records CDCL learned clauses, reconstructs resolution proofs and transports finite models. It includes constant-free inputs, equality refinement and quotient models. The unsigned controls pass 18 Rust tests, 24 original-input compiled-Lean proof checks, ten model checks and 34 documents. Signed single-file controls have 13 proofs, six models and 19 documents, with 21 additional document theorem audits. Original include bundles pass five Rust tests, 11 initial proof checks and five models/documents. The bundle exporter passes 15 original-input proof documents and 14 invalid export controls. It recovers the three duplicate-name cases through unique document labels, with original file/name citations, and passes 25 source/document theorem audits. Its successors remove duplicate proof reconstruction, preserve all 15 documents byte for byte and pass 25 typed protocol controls. Thirteen further theorem audits cover printed-row resource errors; an original-input overflow fixture confirms resource exit 4 without partial output. The shared bundle entry also accepts all 37 retained single-file certificates. Using the bundle producer for those original inputs yields 37 checked proof documents and 16 checked model documents, so product integration can use one entry for single files and bundles. Six small original-byte EPR cases now have kernel proofs: three CNF inputs-refutations covering a selected include and a transitive-equality chain, a universally quantified FOF conjecture in standalone and selected-include forms, and a second conjecture selected from a file containing two goals. The two-goal case has a compiled checked countermodel for its first conjecture and a kernel proof for its second; it has no whole-file theorem. An isolated safe-Rust generator now emits the original-bundle front/task modules: eleven generated modules pass 59 kernel audits, with three altered-observation refusals and six protocol/resource controls. Three altered preprocessing observations are refused. Assembly, certificate replay and acceptance composition still need generated equations. Independent acceptance review and installed strategy integration remain open. These are isolated controls, not product capabilities or performance results; the checklist records their receipts.

## Search

1. Discover a larger strategy schedule on training inputs disjoint from evaluation corpora. The [frozen corpus](../benchmarks/v4-corpus/README.md) contains 256 training, 64 validation and 256 held-out problems in disjoint filename families; the original benchmark families are excluded. Select strategies using problem features and allow unequal slice lengths. After the initial pilot, a [complete 2,048-cell training matrix](../benchmarks/v4-training/README.md) used the launcher producer routes on all 256 training inputs. The baseline checked 72 tasks; the union of eight strategies checked 74. The matrix uses two-second producer slices and one task per problem. Longer slices and schedule selection remain open; the default schedule is unchanged. Validation and held-out outcomes are unused.
2. Add AVATAR splitting. First measure a producer-only expansion and its certificate cost; introduce a checked split rule only if needed, with an explicit definition for each fresh predicate.
3. Add deterministic learned clause selection. Record how the model was trained and keep evaluation inputs out of training.
4. Control the passive set with lazy orphan deletion, count-based resource limits and a more compact representation.
5. Improve unit-equality search through ground joinability, connectedness, critical-pair scoring and goal transformation.
6. Add literal-selection and ordering variants to the schedule, including KBO weight schemes and an LPO slice.
7. Profile before changing indexes. Candidates include discrimination trees, fingerprints, feature vectors and cached rewriting.
8. Add equality factoring to certificates with a checked inference rule.
9. Add ground instantiation with SAT for effectively propositional problems.
10. Add a parallel portfolio with an explicit shared resource budget and reproducible strategy records.
11. Revisit the remaining v3 search targets, including CSR114+13, CSR116+2, HWV116+1, COM146+1, COM123+1, CSR239+1 and the local block-21000 fixture. Historical time and memory observations are leads for profiling, not current measurements.

## Runtime and checking cost

12. Reduce time spent on unsuccessful schedule slices. Measure search, checking and output separately as well as end to end.
13. Reduce fixed per-problem costs, including goal listing and checker startup. Profile large-input preprocessing separately from short-certificate replay.
14. Replace repeated list-indexed clause lookup with an array store and improve substitution lookup where profiling justifies it. Preserve exact acceptance and rejection behavior; validate the actual runtime path.
15. Investigate position-only certificate nodes and chain nodes for demodulation, subsumption resolution and unit deletion. Each new representation needs checked semantics and malformed-certificate tests.
16. Improve the extracted clausifier's runtime while preserving its connection to the checked preprocessing definitions.

## Input coverage

17. Support larger theories currently rejected by byte limits. Evaluate decoding cost and premise selection before increasing limits.
18. Repeat the clausification-refusal census against the final v3 limits, then address the remaining cases.
19. Address formula height, term depth, literal-count bounds and memory use during signed-goal setup. Limits must remain explicit until the corresponding paths are validated.
20. Resolve the remaining small frontend gaps: non-ASCII comments, the `assumption` role and typed declarations found in otherwise FOF/CNF inputs. This does not move general typed reasoning into v4.

## Satisfiability

21. Certify satisfiability for problems with only infinite models. A saturated clause set needs a proved model construction or another checked satisfiability argument before it can yield a positive status.
22. Improve finite-model search: instance-size limits, incremental solving across domain sizes, maximum-size detection and domains guided by inferred sorts. A smaller sorted search must still produce a model checked against the original unsorted input.
23. Address model-evaluation costs and cases that exceed the existing budget. Consider per-path corollaries of the export determination theorem where they help document the result.

## Output and kernel replay

24. Export complete TSTP refutations for signed include bundles, including cited-premise certificates, and for signed single files with distinct objects. Cover goal and inputs-refutation paths, nested includes, selection lists and original statement identities. Unsupported paths must continue to refuse export explicitly.
25. Extend kernel replay beyond its current depth and runtime limits. Work includes the bundled independent kernels, structurally recursive preprocessing counterparts and passing certificates as Lean values.
26. Reassess the certificate-size cap after item 14 is integrated and measured. Do not raise it based only on an isolated data-structure result.

## Acceptance and evaluation

The entire Rust engine and runtime must remain safe Rust. External libraries are permitted when their algorithms help and they satisfy that constraint; testing and integration dependencies must remain distinguishable from runtime dependencies. New tooling does not require Python.

Checker changes must preserve or prove the intended acceptance semantics. Lean proofs must stay within the existing axiom policy: `propext`, `Classical.choice` and `Quot.sound`. Changes to an acceptance boundary receive an independent review, executable rejection tests and the relevant axiom audits. Source maps, import closures and installation checks must describe the source actually built.

Use focused replay and regression tests while implementing. Run a new end-to-end comparison only on a stable candidate, using fixed resource limits and preserved inputs. Report checked positive statuses separately from complete requested documents, and solved counts separately from timings on common solves. Strategy training and evaluation must use disjoint corpora. A local speedup or a recovered export path is not evidence that the whole version meets its competitive target.

## Final benchmark: three checking modes

The final v4 benchmark must measure Fang with `--check none`, its default compiled Lean checking, and `--check kernel`. Each mode is compared with the same pinned Vampire binary and configuration used for the v3 release. Record every command and binary hash. Rerun Vampire alongside v4 under the chosen measurement conditions; do not reuse old wall times as a contemporaneous baseline.

Keep the v3 publication format: a Markdown report, a complete TXT problem list, per-occurrence TXT and CSV timings, and a standalone searchable HTML table. Preserve repeated problem IDs as separate occurrences. The HTML must offer a view for each Fang mode, with seconds shown in green when Fang is faster, red when Vampire is faster, and gray for ties or comparisons that do not qualify. Each row must identify its checking mode, trust level, outcome, output completeness and reason for exclusion. An unchecked candidate must never be labeled a verified result.

Freeze the final mode capabilities before selecting commands. The current v3 interface refuses TSTP output in unchecked and kernel modes, and kernel mode requires at least 600 seconds and 4 GiB. It also lacks bundles, conjectures and finite models. These are starting limitations, not assumed capabilities of the final v4. Unsupported inputs or flag combinations must remain visible as such; a quick refusal is not a timing win. Do not compare kernel runs with a larger resource allowance against a smaller Vampire allowance without a separate, explicitly labeled experiment.

Separate the cost-of-checking comparison from the complete-document comparison. For the former, use the same supported input tasks, compatible output settings and resource budgets for all compared modes. Report complete-document coverage separately, including the default-mode TSTP comparison. Publish both full-corpus outcomes and paired timings on common successful outcomes. Label unchecked timings as candidate timings and keep their totals separate from checked results. A whole-command timing difference can also reflect search scheduling and output work; use retained-certificate replay when attributing a difference specifically to checking.
